## 3. 测量工具（已交付并验证）

`src/game/perf/PerfRecorder.ts` + 28 条单测（`tests/perfRecorder.test.ts`）。

关键设计（都对应规格 §F1 的具体禁令）：

| 能力 | 防止的错误 |
|---|---|
| P50/P95/P99/P99.9 + max | 只看平均 FPS |
| `computeLow()` 取最慢 k% 均值再取倒数 | 拿「分位数取倒数」冒充 low% |
| 命中定格单独计数但**不删除** | 用 hit-stop 掩盖真实掉帧 |
| `inactive` 样本排除但总数保留 | 用后台/切场景帧充数或删样本 |
| GPU 耗时拿不到就是 `null` | 用 0 或 CPU 值假装 GPU 数据 |
| 窗口化迟滞（收紧 2 窗 / 恢复 5 窗） | 旧 `Quality.ts`「FPS<40 才收紧」的宽松口径 |

## 4. 为什么桌面帧率数字无效

按用户指示用本机替代核显做性能测试。实测采到：

```
frames 344 / 10s
buckets(以 16.67ms 为单位): {1: 99, 2: 235, 3: 10}
p50 33.3ms   min 16.6ms   max 50.1ms
游戏自报 34 FPS
```

帧间隔全部落在 16.67 的整数倍上（99 / 235 / 10），是典型的 **vsync 锁定后掉到
半数刷新率**的模式。数值本身自洽（统计工具已验证口径正确），**但不能当作游戏性能结论**，原因：

### 4.1 测量期间 CPU 被抢占

```
CPU: Intel i3-4170 @ 3.70GHz  (4 线程, Haswell 世代的入门款)
load average: 2.50 / 3.08 / 3.15
内存: 7.5Gi 总量, 可用仅 2.6Gi

占用 CPU 的进程:
 44.4%  ai.opencode.des   ← 我自己的 agent 运行时
 34.0%  ai.opencode.des
  6.6%  sunshine          ← 屏幕串流/编码
  5.8%  ai.opencode.des
```

测量期间本会话的工具链自身吃掉了 80%+ 的 CPU。**在这种 CPU 争用下测出来的
帧时间反映的是争用，不是游戏。**

### 4.2 这不是 HD 4400 所在的那台机器

`8086:041e`（HD 4400）确实在本机存在，但本机 CPU 是 **i3-4170**，
与用户描述的「Intel HD 4400 低配机」不是同一台机器的性能画像。

### 4.3 因此

- 我**不**写「已达成 60 帧」。
- 我**不**把这个 34 FPS 当作游戏不达标的证据。
- 在 CPU 争用解除前，任何桌面帧率都不可信。

## 5. 获得有效性能结论的条件

按影响从大到小：

1. **停止 sunshine 串流**（它同时吃 CPU 与编码带宽）。
2. **让 agent 空闲**：测量期间不要跑 `vitest`、不要并发开浏览器 tab。
   理想情况是在无 agent 负载的窗口内，用一个独立脚本采集。
3. 若要在**真实低端机**上出 R14 结论，需要一台真的是 HD 4400 的设备；
   本次的 Xiaomi 12S 是旗舰，不具备代表性。
