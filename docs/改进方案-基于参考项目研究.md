## 一、研究的三个关键发现（推翻原预期）

### 1. geometry-duel 的「帧同步」是假确定性 —— 反向印证宿主权威是正确选型

- 它确实是 **lockstep 输入同步**（只传输入、各端全量模拟，`network.js:130-140`），但确定性是半成品：
  host 生成的种子从未被游戏逻辑消费（`this.rng` 全文仅 2 处赋值），击退等模拟路径直接用
  `Math.random()`（`game.js:862-866`），且没有任何状态对账机制。它「能玩」靠的是 PvP 小地图容忍漂移。
- **对本作的结论**：PvE 搜打撤有大量实体与掉落判定，绝不能走这条路；宿主权威 + 状态同步的选型得到反向印证。
- 可搬的是「壳」：Cloudflare Worker(KV) 信令服务器（`worker/index.js` 全套 create/join/signal/poll/leave）、
  host 发起的星型建连、ICE 缓冲+flush（`network.js:699-728`）、STUN 批次轮换重试（`network.js:469-482`）、房间码生成。
- 必须避开的坑：单条不可靠 DataChannel 连 gamestart 都可能丢（它靠信令通道兜底）；断线即永久 stall
  （超时只改状态不处理）；无 TURN 穿透（业界 10-20% 失败率，需 host 中继兜底）；500ms HTTP 轮询信令延迟高。

### 2. geometry-rogue 的 entities/、systems/ 目录是空的

实际是 **815 行单文件场景**，比我们的 GameScene 还小——它不是拆分模板，但它的职责选择
（先拆数据表/HUD/音效/自洽子系统）与大量小模式非常有价值（见第三节清单）。

### 3. chemic 还有大量未吸收资产

create 模式 5 首 BGM（大厅/合成界面）、Consolas 等宽字体、元素角色三视图（img/act/*/a,b,c.png）、
ball.js 物理球池（423 行自包含 Matter.js）、任务/委托系统——见第四节内容计划。

## 二、P0 · 架构治理：GameScene 拆分路线（联机的前置工程）

GameScene 已 6000+ 行。拆分原则（从 geometry-rogue 学到的边界感）：
**先拆不碰玩法的 → 再拆纯模拟的 → 最后拆耦合玩法的**；每步只留薄转发，可回归验证。

| 顺序 | 模块 | 迁走内容 | 备注 |
|---|---|---|---|
| 1 | `data/` 表驱动补全 | 敌人/Boss 原型表、波次**权重表**（现有硬编码概率拆出） | 零风险；修 geometry-rogue `pickEnemyType` 同款缺陷 |
| 2 | `ui/HudCache` 脏检查 | UIScene 每帧 setText 的值比对（现有 setTextSafe 已有雏形，统一成 cache 模式） | 抄 `hud.js:4-27` |
| 3 | `fx/Particles`（环形缓冲） | 粒子/飘字/涟漪；combatTextPool 扩展为统一池 | 避开它的反面教材（对象+splice） |
| 4 | `systems/SpawnDirector` | 波次队列、难度曲线、清空判定 → 输出「生成事件」 | 纯模拟，联机时 host 独占运行 |
| 5 | `systems/CombatResolver` | 伤害计算/暴击/击杀结算/掉落判定 → 产出事件（FX/HUD 订阅） | 判定与表现分离 |
| 6 | `entities/Enemy|Boss` 类 | `_spawn` 拍属性 + per-type AI switch → `{view, body, data}` 组合 | RuntimeEnemy 已有雏形，补行为类 |
| 7 | `systems/ProjectileSystem` | 双方弹幕 + **真对象池** + 穿透 hitSet 去重 | GC 大头 |
| 8 | `core/RunProfile` | 局内属性真身（纯数据）与引擎对象分离，重开局=重建 profile | 抄 `game.js:319-337`；温度/数值挂载于此 |
| 9 | 显式状态机 | enter/playing/cleared/extract/dead 转换守卫集中 | 现散落在 roomState 字符串 |

目标：GameScene < 500 行（create 装配 + update 分发 + 碰撞注册）。
**这也是联机的必要工程**：SpawnDirector/CombatResolver 拆出后，host 才能独占权威模拟。

## 三、P1 · 联机实施路线（Phase M）

### M1 传输壳（2-3 天）
- 信令：Cloudflare Worker + KV 照搬 `worker/index.js` 路由，轮询改 WebSocket/Durable Object
- 建连：host 发起星型拓扑（guest 各连 host 一条 PC，O(n) 通信量）；ICE 缓冲+flush；STUN 分批轮换
- 兜底：穿透失败 → host 中继模式（星型拓扑天然支持）

### M2 同步芯（自研，1-2 周）
- 双 DataChannel：可靠有序（快照/加入离开/游戏开始）+ 不可靠无序（30Hz 状态增量、guest 输入）
- host 权威模拟：SpawnDirector/CombatResolver 只在 host 跑；guest 上报输入意图（低频采样+圆整，抄 `serializeInput` 技巧）
- 客人端：实体插值 + 仅自身移动的本地预测；断线重连 = 全量快照；guest 超时 = host 端 AI 托管
- RNG：掉落/刷怪由 host 单点决定（不需要 geometry-duel 的种子共享那套）

### M3 联机玩法（1 周）
- 共享房间温度/撤离进度；祝福各自选；样本各自拾取
- 队友倒地 → 注入电子复活（贴合「电子即生命」核心机制）

## 五、立即可抄的小模式清单（按收益排序，均可当天完成）

1. **HUD 脏检查缓存**（`hud.js:4-27`）— UIScene 每帧 setTextSafe 的统一化
2. **穿透弹 hitSet 去重**（`game.js:564,584-585`）— 激光/贯穿类武器防重复结算
3. **延迟销毁**（标记 alive，帧末统一 destroy）（`game.js:647-649`）— 迭代中改集合的隐患清除
4. **RunProfile 与引擎对象分离**（`game.js:319-337`）— 配合拆分第 8 步
5. **平台异常折叠**（`main.js:35` 吞 unhandledrejection + fullscreen/orientation 全 try-catch）— APK 稳定性
6. **hitStop 时间缩放式实现**（`game.js:471` dt×0.14）— 与现有 hitStopTimer 互补的备选方案
7. **纹理幂等创建 + 预生成多色纹理**（`game.js:25-31,369-376`）— 染色系统已部分做到，补齐弹幕类

## 六、明确不做

- ❌ lockstep 帧同步（假确定性，PvE 不适用）
- ❌ 内置第三方引擎 WebView（系统 WebView 120 功能健全）
- ❌ geometry-duel 的 JSON 快照序列化（换二进制 + delta）

### 待办（沿用原方案）

### 新增经验（补充到原"不做"清单）

- ❌ 用文本锚点脚本批量改代码 —— 半套执行会留下"声明在、创建丢失"的残状态，排查成本极高；一律用 Edit 精确修改 + 每步验证
- ❌ 改完不立即 commit —— `git checkout` 排查会丢弃未提交改动
- ❌ 在 iframe 里跑 WebGL 游戏做验证 —— RAF 被冻结，产生"卡死"假象，应直连页面或真机验证
